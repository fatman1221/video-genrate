# 故障速查

> 先看这张总表，再往下找细节。

## 总表

| 现象 | 原因 | 处理 |
|---|---|---|
| 后端启动报 `EEXIST` / `PermissionError` | PYTHONPATH shim 劫持 `os.mkdir` | `unset PYTHONPATH` |
| Vite 启动 1~2 秒自己退出，日志有 `SAFE_DELETE` | NODE_OPTIONS shim 拦截批量删除 | `unset NODE_OPTIONS` |
| **命令 exit 0 但毫无输出、进程 0.3 秒就退出** | `env -u` 被 shim 遮蔽成空操作 | 见 [下面](#env--u-会静默失效) |
| 后端连不上库 | 容器没起 / 端口不对 | `docker compose up -d`；核对 `DATABASE_URL` 端口 |
| 项目列表为空 | 没恢复 dump | 见 [换机迁移](换机迁移#3-恢复数据库可选但推荐--否则是空库) |
| 图片 / 视频 404 | 没解包 storage | 见 [换机迁移](换机迁移#4-恢复素材若上一步做了) |
| 视频合成失败 | 缺 ffmpeg | 见 [快速开始](快速开始#6-ffmpeg-安装) |
| `docker compose up` 影响了别的项目 | 目录名与别的 compose 项目重名 | 见 [换机迁移](换机迁移#2-启动-postgresql) |
| 前端页面空白 | `vite.config.js` 白名单缺图标 | 把新图标加进 `MUI_ICONS` 并清 `.vite` |
| 设置页某引擎显示"不可用" | 服务没起 / 凭证没填全 | 见 [模型引擎与配置](模型引擎与配置#设置里显示不可用) |
| 节点显示"有产物却是待执行" | 状态漂移 | 见 [下面](#节点状态漂移) |
| wiki 推送报 `Repository not found` | wiki 仓库要网页端保存过首屏才会被创建 | 见 [下面](#wiki-推送报-repository-not-found) |

## env -u 会静默失效

### 现象

命令**exit 0 但毫无输出**，进程 0.3 秒就退出。日志一片空白，像是"什么都没跑"。

### 原因

部分机器 PATH 上存在 `~/.local/bin/env` —— 一个 uv 安装器留下的**只做 PATH 前插的 shim 脚本**。

**它是否遮蔽真正的 `/usr/bin/env` 取决于 PATH 顺序**：

- `~/.local/bin` **排在 `/usr/bin` 前面**（常见于用户交互终端，`.zshrc` 会前插）→ shim 生效，
  它既不转发参数也不执行命令，于是 `env -u PYTHONPATH python -m uvicorn ...`
  变成一句**什么都不做的空操作**
- `~/.local/bin` 排在后面 → `env` 就是真正的 `/usr/bin/env`，`env -u` 正常生效

> 也就是说：**`env -u` 不是错的，只是有条件**。同一台机器上，AI 工具 shell 与
> 用户终端可能表现不同。

### 处理（推荐用 shell 内建 `unset`，无条件正确）

```bash
unset PYTHONPATH
python -m uvicorn app.main:app --host 127.0.0.1 --port 8077

# 前端同理
unset NODE_OPTIONS
./node_modules/.bin/vite --host 127.0.0.1 --port 5180 --strictPort
```

写成一行时用 `&&` 串联：

```bash
unset PYTHONPATH && python -m uvicorn app.main:app --port 8077
```

若确实要用 `env -u`，可绕过 shim 用绝对路径：`/usr/bin/env -u PYTHONPATH ...`。

### 诊断

```bash
type -a env
# 首个是 /usr/bin/env → 正常
# 首个是 ~/.local/bin/env → 中招
```

## Python 起不来：`PermissionError: EEXIST`

### 原因

某些宿主（如 WorkBuddy / CodeBuddy）会注入 `PYTHONPATH`，其中 `sitecustomize.py` 劫持了
`os.mkdir` / `pathlib.Path.mkdir`。**目录已存在时它抛 `PermissionError(EEXIST)` 而不是 `FileExistsError`**，
导致 `Path.mkdir(exist_ok=True)` 直接崩（pathlib 只捕获 `FileExistsError`）。

### 处理

```bash
unset PYTHONPATH
```

### 诊断

```bash
python -c "import os; print(os.mkdir.__module__)"
# 输出 sitecustomize → 中招
```

> 在普通终端里 `PYTHONPATH` 不存在，`unset` 是空操作、可安全保留。

## Vite 秒退：`SAFE_DELETE_BULK_CONFIRM_REQUIRED`

### 原因

某些宿主通过 `NODE_OPTIONS` 注入 safe-delete 保护，**单轮删除超过 50 个文件会被拦截**。
而 Vite 在依赖变化时会清空整个 `node_modules/.vite`（数百文件）→ 被拦 → 进程退出。

### 处理

```bash
unset NODE_OPTIONS
./node_modules/.bin/vite --host 127.0.0.1 --port 5180 --strictPort
```

必要时先清缓存（`shutil.rmtree` 比 `rm` 更可靠 —— 本机 `rm` 也可能被同一个 shim 拦）：

```bash
python -c "import shutil; shutil.rmtree('node_modules/.vite', ignore_errors=True)"
```

### 配套注意

`vite.config.js` 里维护了 MUI 图标的预构建白名单（`MUI_ICONS`）：
**新增图标时必须同步登记**，否则首次引用就会触发「重新预构建 → 清空缓存」→ 撞上同一条保护。

## 节点状态漂移

### 现象

节点图里某个节点"有产物，却显示待执行"。

### 原因

合成时内部完成了拼接，但「剪辑」节点没被标记完成 —— 早期版本的 `handle_compose_video` 漏了 `complete_step("editing")`。已修。

### 排查

```bash
# 看节点视图
curl -s http://127.0.0.1:8077/api/projects/{id}/pipeline | python3 -m json.tool
```

若仍有异常，检查对应 handler 是否在每个终态都调用了 `complete_step()`。
另外：回退后重跑完成时若无法前向推进（跳跃迁移被拒），`complete_step` 有 force 自愈机制。

## 后台服务莫名其妙消失

`nohup ... &` 起的服务会在**对话结束时被回收**。

需要常驻的服务，用工具的后台任务机制启动，或在**用户自己的终端**里起。

## git push / fetch 连不上

### 先分清「哪种连不上」

**`api.github.com` 通不代表 `github.com` 通** —— 两者是不同 IP，而 **`git push` 走的是 `github.com`**。
所以会出现「API 能查、push 就是推不上去」这种看起来矛盾的现象。

```bash
# 分别测（注意是两个不同的域名）
nc -z -G 5 github.com 443     && echo "github.com OK"     || echo "github.com 不通"
nc -z -G 5 api.github.com 443 && echo "api.github.com OK" || echo "api.github.com 不通"
```

> ⚠️ `nc -z` 通过**不代表 TLS 能成** —— 存在防火墙回 SYN-ACK 但握手被阻的情况。
> 要确认真能通，用 `curl --max-time 10 https://github.com -o /dev/null -w '%{http_code}'`。

### 原因 A：git 里配了失效代理

全局 `~/.gitconfig` 里配了 `http.proxy`（如 Clash 的 `127.0.0.1:7897`），但代理客户端没启动。

**只在本仓库**覆盖为空，不影响其他项目：

```bash
git config --local http.proxy ""
git config --local https.proxy ""
```

或临时一次性绕过：

```bash
git -c http.proxy= -c https.proxy= push origin main
```

### 原因 B：代理开着，但规则挡了 github.com

某些代理客户端会对 `github.com` 命中 **REJECT 规则**（0.12 秒硬失败），而 `google.com` 正常。
表现很迷惑：**"代理明明开着"**。

```bash
# 走代理分别测
curl -s -o /dev/null -w "google:  %{http_code} %{time_total}s\n" --max-time 8 -x http://127.0.0.1:7897 https://www.google.com
curl -s -o /dev/null -w "github:  %{http_code} %{time_total}s\n" --max-time 8 -x http://127.0.0.1:7897 https://github.com
```

若 google 通、github 秒失败 → 去代理客户端把 `github.com` 的路由规则改成走可用节点，
或切到全局模式。

### 原因 C：直连也被阻断

`github.com` 的 IP 在部分地区不可达。确认：

```bash
nslookup github.com            # 看解析到哪个 IP
curl -s -o /dev/null -w "%{http_code}\n" --max-time 10 --noproxy '*' https://github.com
```

此时只能走代理，或等网络恢复。

### 网络恢复后自动重推

```bash
for i in $(seq 1 24); do
  if nc -z -G 5 github.com 443 2>/dev/null; then
    git -c http.proxy= -c https.proxy= push origin main && break
  fi
  sleep 20
done
```

## 前端页面空白

1. 打开浏览器控制台看报错
2. 若是 `Failed to resolve import @mui/icons-material/Xxx` → 把 `Xxx` 加进 `vite.config.js` 的 `MUI_ICONS` 白名单
3. 清掉 `node_modules/.vite` 重启

## wiki 推送报 Repository not found

### 现象

```text
$ git clone https://github.com/<owner>/<repo>.wiki.git
remote: Repository not found.
fatal: repository 'https://github.com/<owner>/<repo>.wiki.git/' not found
```

而主仓库的 fetch / push 一切正常。

### 原因

GitHub 的 wiki 是**另一个独立的 git 仓库**（`<repo>.wiki.git`），但它
**只有在网页端保存过第一个页面之后才会被创建**。在此之前：

- 没有任何 REST / GraphQL API 能创建 wiki 页面
- 直接 `git push` 到该地址 **也不会**替你建出仓库，只会返回 `not found`
- `has_wiki: true` 只表示功能开关是开的，不代表 git 后端已存在

### 处理

手工点一次，约 10 秒：

1. 打开 `https://github.com/<owner>/<repo>/wiki/_new`
2. 标题填 `Home`，正文随便写一个字，点 Save
3. 回到仓库目录执行：

```bash
./scripts/publish_wiki.sh
NO_PROXY_GIT=1 ./scripts/publish_wiki.sh   # 本机 git 代理指向未启动的客户端时
```

**更省事的做法：加 `--wait`。** 脚本先把要点的链接打给你，然后原地轮询等待
（默认 30 分钟），你点完 Save 它自己接上发布，不用来回通知：

```bash
NO_PROXY_GIT=1 ./scripts/publish_wiki.sh --wait      # 等 30 分钟
NO_PROXY_GIT=1 ./scripts/publish_wiki.sh --wait 600  # 自定等待秒数
```

首屏内容会被脚本整体覆盖，所以正文写什么无所谓。
