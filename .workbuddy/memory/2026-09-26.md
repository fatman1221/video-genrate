### 本轮定位并修复的真实缺陷
1. **ffmpeg 卡死（关键）**：PIL `img.save(..., optimize=True)` 写出的 PNG 会让 ffmpeg(libpng) 在
   `-loop 1` 读取时**无限阻塞**（仅个别图像触发，概率约 1/4，表现为 5s 视频渲染 >600s 超时）。
   - 修复一：`_save_png_std()` 统一用 `interlace=False`、默认压缩写 PNG，不再用 `optimize=True`
   - 修复二：`image_to_video` 入口先归一化输入图（任意来源）再渲染
   - 修复三：`run_ffmpeg` 改用**看门狗线程 + `start_new_session` 进程组强杀**；旧实现把超时判断
     放在 `for line in proc.stdout` 循环里，ffmpeg 不输出时永远触发不了超时
   - 验证：坏图 0.4s 完成，其余图 0.3–0.4s
2. **混音失败**：主视频无音轨时 `mix_audio` 的 `[0:a]` 不存在 → 已改为检测音轨后决定是否混入原声
3. **批量分组任务被误当可执行任务** → 已排除
4. **成片只剩一个镜头（时长 5s ≠ 20s）**：合成时主视频取了"最新一条 VIDEO 素材"，
   而画质增强产出的单镜头片段把整片顶掉了。
   - 修复：主视频**必须**由 `_ordered_shot_videos()` 按镜头序号拼接；仅在 `source_asset_ids`
     与当前镜头视频完全一致时才复用已有拼接；显式 `video_asset_id` 才允许覆盖
   - 顺带：`_ordered_shot_videos()` 优先取镜头的增强版（`enhanced_video_asset_id`）；
     项目级 `enhance_video` 优先作用于 `role="merged"` 的粗剪；合成时若粗剪已有增强版则采用
5. **项目永远无法进入 COMPLETED**：质检 `status=WARN` 既不通过也不触发修复，而"人物一致性"
   检查需 VLM → 永远 WARN → 永久卡在中间态。
   - 修复：以 **FAIL=0 即可交付** 为完成判据（WARN 记为提示不阻塞）；有 FAIL 才走自愈重跑
6. **孤儿 RUNNING 任务**：`maintenance()` 改为 `reclaim_stale(stale_seconds=0)`，
   进程启动时无条件回收（启动即无任务在跑），实现断点恢复。实测日志 `reclaimed: 1`

## 连续剧（Series）分层改造

### 需求背景
用户问「脚本应该就一个还是多个，我想的是多个连续剧」。核查发现：`Project.scripts` 本来就是
一对多，但语义是**多版本草稿**（有 `version` 字段），且 `Storyboard/Scene/Shot` 全部只挂
`project_id`、**与 script 毫无关联**。所以直接塞多个脚本会让多集镜头混在同一条流水线，
且只能出一个成片。结论：**「脚本多个」不够，必须在结构上插入「集」层。**

### 方案（用户选定）
**Series → Project（一集 = 一个 Project）→ 现有流水线**，另加**系列级角色库**保证主角跨集一致。
取舍理由：每集复用整套已验证能力（独立 workflow、节点回退/审核/重生成/成片），
改动集中在「加一层归属」，风险最低。另一方案（Project 下加 `episodes` 表 + 各表加 `episode_id`）
需数据迁移且回退/审核/统计逻辑要按集重写，未采用。

### 数据模型
- 新增 `series` 表；`projects` 加 `series_id`(ON DELETE SET NULL) + `episode_no`
- `characters` 加 `series_id`(CASCADE)，且 `project_id` 改为**可空**（系列级角色不属任何一集）
- `database.py` 迁移扩成三步：`ensure_columns()` → `ensure_nullable()`(DROP NOT NULL) →
  `ensure_foreign_keys()`(查 pg_constraint 后 ADD CONSTRAINT)。老库启动即对齐，无需手工干预。

### 关键设计边界：读用「池」，写只动「本集」
新增 `services/characters.py`：
- `character_pool(db, project)` = 本集角色 + 所属系列的系列级角色 → 用于分镜引用解析、
  planner 角色分配、界面展示、节点统计（全部改用它）
- `own_characters(db, project_id)` = 仅本集自有 → 用于回退/清空引用等写操作
**原因**：系列级角色的参考图是全系列共享的，若某一集回退时清掉会连带废掉其它集的主角形象。
因此 `rollback_to("character")` 只清本集；`regenerate_stage("character")` 对系列级角色
只在缺图时补齐、不重置。

### 本轮修复的两个真实缺陷
1. **planner 把演示角色名写死**（`main_character = "小智" if seq % 3 != 0 else "阿格"`）：
   项目里定义了真实角色后，分镜引用不上，`image_prompt` 里还残留「角色：小智」这种不存在的名字。
   → 改为优先按传入角色池轮换 `cast[(seq-1) % len(cast)]`，无角色时才回落内置演示角色。
2. **pipeline 重建分镜时按「名字」匹配角色，而 planner 给的是「id」** → 引用恒为空。
   → 把解析逻辑统一下沉到 `characters.resolve_character_ids()`（id / 中文名都能解析），
   `content_skills._resolve_character_ids` 与 `pipeline` 共用同一实现，避免两套规则再次跑偏。

### 交付
- Skill 73 → **84**（新增 `category="series"` 11 个）；REST 新增 `/api/series` 系列 7 个端点
- 前端：新增 `SeriesList` / `SeriesDetail` 两页 + `MiniRing` 公共组件；导航加「项目 | 连续剧」
  Tab；项目卡片与详情页显示「第 N 集」并可跳回所属剧

### 新环境坑（重要，跨项目复用）
**`NODE_OPTIONS` 注入的 node-language-shim.cjs 会杀掉 Vite dev server。**
- 现象：`[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":324,...,"targets":[".../node_modules/.vite"]}`，

### ⚠️ 事故复盘：docker compose 用目录名当项目名，顶掉了另一个项目的容器

**经过**：我把自带数据库编排放在 `deploy/` 目录（想当然的名字），
执行 `POSTGRES_PORT=5433 docker compose up -d` 时，compose 以目录名 `deploy`
作为项目名，而本机**恰好存在**另一个同名 compose 项目
（`~/Desktop/code/trade/trade-intelligence-platform/deploy`）。
它把该项目的 `deploy-postgres-1` 当成自己的 `postgres` 服务**重建**了 ——
原容器消失。

**数据是否丢**：**没丢**。数据在命名卷 `deploy_postgres-data` 里，
容器重建不影响卷。实测该卷仍含 3 个库（`trade_intelligence` 14 表有数据、
`video_agent_studio` 完好）。⚠️ 但 `docker volume inspect` 报的 CreatedAt
变成了当天，**不能据此判断卷被重建**，必须挂载进去实查。

**恢复**：回原项目 compose 目录执行（必填变量从运行中容器取回，
`REDIS_PASSWORD` 取自 `docker inspect --format '{{json .Config.Cmd}}'`），
`docker compose up -d postgres` 即还原（镜像/卷/端口/网络/环境变量全部一致）。

**最终对策**
1. 目录改名 `deploy/` → `local-postgres/`（唯一名，项目名派生后天然隔离）
2. 本机 compose 是 **v2.2.3，不支持文件里的顶层 `name:` 字段**
   （报 `Additional property name is not allowed`）→ 只能在文件头写明警告 + 目录名隔离
3. 在 compose 文件头写清事故经过与「勿放进通用名目录」

**教训**：`docker compose up` 不是「只影响本目录」的操作。
动手前先 `docker compose ls -a` 看本机有哪些项目名。
